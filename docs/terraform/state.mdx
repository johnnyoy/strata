# Terraform State

<Level show="short">
Terraform stores a mapping of config → real resources in `terraform.tfstate`. This is how it knows what exists, what changed, and what to destroy.

**Store state remotely** — never commit it to Git:

```hcl
terraform {
  backend "s3" {
    bucket         = "my-tf-state"
    key            = "prod/terraform.tfstate"
    region         = "us-east-1"
    dynamodb_table = "tf-state-lock"
  }
}
```
</Level>

<Level show="medium">
**Why state exists**

State maps each `resource "aws_instance" "web"` in your config to the real AWS resource ID (`i-0abc123...`). Without it, Terraform can't know what it manages vs what already existed.

State also stores attribute values Terraform needs for plan/apply but can't read back from the API (e.g., passwords it generated).

**Remote backends — options**

| Backend | Use case |
|---------|---------|
| `s3` + DynamoDB lock | AWS-hosted projects (most common) |
| `azurerm` | Azure-hosted projects |
| `gcs` | GCP-hosted projects |
| `http` | Custom REST endpoint |
| Terraform Cloud / HCP Terraform | Managed remote state + UI |

**S3 backend setup**

```hcl
terraform {
  backend "s3" {
    bucket         = "my-tf-state"
    key            = "envs/production/terraform.tfstate"
    region         = "us-east-1"
    encrypt        = true
    dynamodb_table = "terraform-state-lock"  # prevents concurrent apply
  }
}
```

Create these before first `terraform init`:

```bash
aws s3api create-bucket --bucket my-tf-state --region us-east-1
aws dynamodb create-table \
  --table-name terraform-state-lock \
  --billing-mode PAY_PER_REQUEST \
  --attribute-definitions AttributeName=LockID,AttributeType=S \
  --key-schema AttributeName=LockID,KeyType=HASH
```

**Workspaces — multiple environments from one config**

```bash
terraform workspace new staging
terraform workspace new production
terraform workspace list
terraform workspace select staging
terraform apply   # state stored at envs/<workspace>/terraform.tfstate
```

Access in config:

```hcl
locals {
  instance_type = terraform.workspace == "production" ? "t3.medium" : "t3.micro"
}
```

**`terraform state` commands**

```bash
terraform state list                         # list all managed resources
terraform state show aws_instance.web        # full attributes of one resource
terraform state mv aws_instance.web aws_instance.app   # rename without destroying
terraform state rm aws_instance.old          # remove from state (resource kept in AWS)
terraform state pull                         # print raw state JSON
```
</Level>

<Level show="long">
**State internals**

`terraform.tfstate` is JSON. Key sections:

```json
{
  "version": 4,
  "terraform_version": "1.7.0",
  "serial": 42,            // increments on every change
  "lineage": "abc-...",    // unique ID for this state file
  "resources": [
    {
      "mode": "managed",
      "type": "aws_instance",
      "name": "web",
      "provider": "provider[\"registry.terraform.io/hashicorp/aws\"]",
      "instances": [{
        "schema_version": 1,
        "attributes": { "id": "i-0abc123", ... }
      }]
    }
  ]
}
```

**Locking**

Remote backends implement state locking to prevent two `terraform apply` calls from corrupting state simultaneously. DynamoDB stores a `LockID` item with metadata about who holds the lock.

```bash
terraform force-unlock LOCK_ID   # release a stuck lock (use carefully)
```

**Importing existing resources**

When resources exist before you started using Terraform, import them:

```bash
# CLI import (Terraform < 1.5)
terraform import aws_security_group.allow_http sg-0abc123
```

From Terraform 1.5+, use `import` blocks for reviewable, GitOps-friendly imports:

```hcl
import {
  to = aws_security_group.allow_http
  id = "sg-0abc123"
}

resource "aws_security_group" "allow_http" {
  # fill in config to match existing resource
}
```

Then run `terraform plan` to verify no changes, then `terraform apply` to write state.

**`terraform refresh` and drift**

```bash
terraform refresh   # update state to match real infrastructure (deprecated; use plan -refresh-only)
terraform plan -refresh-only   # show what drift exists without applying
terraform apply -refresh-only  # update state to match reality without changing resources
```

**Sensitive values in state**

State may contain sensitive data (DB passwords, private keys). Always:
- Enable S3 server-side encryption (`encrypt = true`)
- Use IAM to restrict who can read the S3 object
- Mark sensitive outputs: `sensitive = true` (hides from CLI output but not state file)

```hcl
output "db_password" {
  value     = random_password.db.result
  sensitive = true
}
```

**State file migration**

Moving from local to remote backend:

```bash
# 1. Add backend block to config
# 2. Run init — Terraform prompts to copy local state
terraform init
# "Do you want to copy existing state to the new backend? [yes]"
```
