# SQL Queries

<Level show="short">
SQL reads like English. Select columns, name your table, add conditions.

```sql
SELECT name, email
FROM users
WHERE active = true
ORDER BY name
LIMIT 10;
```
</Level>

<Level show="medium">
The logical order SQL clauses execute (not the order you write them):

`FROM` → `JOIN` → `WHERE` → `GROUP BY` → `HAVING` → `SELECT` → `ORDER BY` → `LIMIT`

**Joins**

```sql
-- INNER JOIN: only rows with a match in both tables
SELECT u.name, o.amount
FROM users u
JOIN orders o ON o.user_id = u.id;

-- LEFT JOIN: all users, even those with no orders
SELECT u.name, COUNT(o.id) AS order_count
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
GROUP BY u.id, u.name;
```

**Aggregation**

```sql
SELECT
  status,
  COUNT(*) AS total,
  AVG(amount) AS avg_amount
FROM orders
GROUP BY status
HAVING COUNT(*) > 10
ORDER BY total DESC;
```

**Subqueries**

```sql
-- Scalar subquery
SELECT name, (SELECT COUNT(*) FROM orders WHERE user_id = u.id) AS order_count
FROM users u;

-- IN subquery
SELECT * FROM products
WHERE category_id IN (SELECT id FROM categories WHERE active = true);
```
</Level>

<Level show="long">
**Query execution plan**

Before running your query, the database optimizer generates an **execution plan**. Use `EXPLAIN ANALYZE` to see it:

```sql
EXPLAIN ANALYZE
SELECT u.name, COUNT(o.id)
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
GROUP BY u.id;
```

Key nodes to understand:
- **Seq Scan** — full table scan; fine for small tables, bad for large ones
- **Index Scan / Bitmap Index Scan** — uses an index to find rows
- **Hash Join / Nested Loop / Merge Join** — join strategies; optimizer picks based on statistics

**Indexes**

```sql
-- Basic index (speeds up WHERE and JOIN on user_id)
CREATE INDEX idx_orders_user_id ON orders(user_id);

-- Partial index (index only active users — smaller, faster)
CREATE INDEX idx_active_users ON users(email) WHERE active = true;

-- Covering index (index includes all columns needed — avoids table lookup)
CREATE INDEX idx_orders_cover ON orders(user_id) INCLUDE (amount, status);
```

Index trade-off: faster reads, slower writes. Don't index every column — index what you filter and join on.

**Window functions**

```sql
SELECT
  name,
  salary,
  AVG(salary) OVER (PARTITION BY department) AS dept_avg,
  RANK() OVER (PARTITION BY department ORDER BY salary DESC) AS dept_rank
FROM employees;
```

Window functions compute across a "window" of rows without collapsing them (unlike `GROUP BY`). Invaluable for running totals, rankings, lead/lag patterns.

**CTEs (Common Table Expressions)**

```sql
WITH monthly_revenue AS (
  SELECT
    DATE_TRUNC('month', created_at) AS month,
    SUM(amount) AS revenue
  FROM orders
  WHERE status = 'completed'
  GROUP BY 1
),
ranked AS (
  SELECT *, RANK() OVER (ORDER BY revenue DESC) AS rnk
  FROM monthly_revenue
)
SELECT * FROM ranked WHERE rnk <= 3;
```

CTEs are named subqueries — they improve readability and let you reference the same result multiple times. In PostgreSQL, they're materialized by default (evaluated once), which can be a performance win or loss depending on the query.

**Transactions and isolation**

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;  -- or ROLLBACK if something went wrong
```

Isolation levels (ANSI):
| Level | Dirty read | Non-repeatable read | Phantom read |
|-------|-----------|---------------------|--------------|
| READ UNCOMMITTED | possible | possible | possible |
| READ COMMITTED | prevented | possible | possible |
| REPEATABLE READ | prevented | prevented | possible |
| SERIALIZABLE | prevented | prevented | prevented |

PostgreSQL defaults to `READ COMMITTED`. Use `REPEATABLE READ` or `SERIALIZABLE` when your logic depends on stable snapshots across multiple statements.

**N+1 queries**

The classic ORM trap: fetching 100 users, then running 1 query per user to get their orders = 101 queries. Fix with eager loading (`JOIN` or `IN` clause) or use the ORM's include/preload feature.
</Level>
