# Docker Networking

<Level show="short">
Docker containers are isolated by default. Use `--network` to let containers talk to each other, and `-p` to expose ports to the host.

```bash
docker network create mynet
docker run --network mynet --name api myapp
docker run --network mynet --name db postgres
# "api" container can reach "db" by hostname
```
</Level>

<Level show="medium">
Docker provides several network drivers. The most common are **bridge** (default), **host**, and **none**.

**Bridge network**

```bash
# Default bridge: containers isolated, no DNS by name
docker run -d --name c1 alpine sleep 1000
docker run -d --name c2 alpine sleep 1000
# c1 cannot reach c2 by name on the default bridge

# User-defined bridge: DNS by container name works
docker network create mybridge
docker run -d --name c1 --network mybridge alpine sleep 1000
docker run -d --name c2 --network mybridge alpine sleep 1000
docker exec c1 ping c2   # works!
```

**Publish ports**

```bash
docker run -p 8080:80 nginx       # host:container
docker run -p 127.0.0.1:8080:80 nginx  # bind to localhost only
docker run -P nginx               # auto-assign host ports
docker port <container>           # show port mappings
```

**Docker Compose** (recommended for multi-container setups):

```yaml
services:
  web:
    build: .
    ports:
      - "3000:3000"
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: secret
```

All services in a Compose file share one network by default — `web` can reach `db` by the service name `db`.
</Level>

<Level show="long">
**Under the hood: Linux networking**

Docker uses Linux network namespaces. Each container gets its own network namespace with a virtual Ethernet pair (`veth`). One end lives in the container as `eth0`; the other connects to a Linux bridge (`docker0` for the default bridge, or a named bridge for user-defined networks).

```
 Host                         Container A
┌────────────────────┐        ┌─────────────────┐
│  docker0 bridge    │        │  eth0 (10.0.1.2) │
│  10.0.1.1          │◄──────►│                  │
│  veth123 (host end)│        └─────────────────┘
└────────────────────┘
```

**iptables / nftables**: Docker automatically inserts rules to:
- NAT outbound traffic from containers to the host IP
- Forward traffic from published host ports into the container

**DNS resolution** (user-defined networks only): An embedded DNS server at `127.0.0.11` resolves container names and service names. The default bridge uses `/etc/hosts` only — no dynamic DNS, which is why user-defined bridges are strongly preferred.

**Network drivers**

| Driver | Use case |
|---|---|
| `bridge` | Single host, isolated containers |
| `host` | Max performance, no isolation (Linux only) |
| `overlay` | Multi-host (Docker Swarm / Kubernetes) |
| `macvlan` | Container needs its own MAC/IP on LAN |
| `ipvlan` | Like macvlan but shares MAC |
| `none` | No networking at all |

**Overlay networking (Swarm)**

Overlay networks span multiple Docker hosts using VXLAN tunnels. Each node runs a gossip protocol to distribute routing. In practice, Kubernetes (with CNI plugins like Calico or Cilium) is the modern choice for multi-host networking.

**Security considerations**

- Containers on the same bridge can reach each other unless you set `--icc=false` on the daemon.
- Publishing on `0.0.0.0` exposes to all interfaces, including external — bind to `127.0.0.1` for internal-only services.
- Use network segmentation in Compose: put your DB on an internal network with `internal: true` so it's unreachable from outside.

```yaml
networks:
  frontend:
  backend:
    internal: true

services:
  web:
    networks: [frontend, backend]
  db:
    networks: [backend]   # unreachable from outside
```
</Level>
